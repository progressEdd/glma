# Debug Log: 2026-04-10

**Context:** Phase 8 execution (ARCHITECTURE.md & Export Polish), then live dogfooding session

## Issues Found

### 1. Module Grouping Off-by-One for 2-Segment Paths [FIXED]

**File:** `src/glma/export.py` → `_get_module_name()`

**Problem:** For paths like `db/store.py` (2 segments), the function returned the filename stem (`store`) instead of the directory name (`db`). The threshold was `>= 3` segments, which only worked for paths like `src/glma/db/store.py`.

**Fix:** Changed threshold to `>= 2` segments. For any path with directory + filename, use the directory as module name.

**Root cause:** Original logic assumed all indexed paths would have a `src/glma/` prefix (3+ segments). When indexing from a subdirectory or flat structure, 2-segment paths were misclassified.

---

### 2. Module Dependencies All Showed "no external dependencies" [FIXED]

**File:** `src/glma/export.py` → module dependency computation in `generate_architecture_md()`

**Problem:** The module dependency graph showed zero edges because:
1. Most Python imports are **unresolved** (self-referential: `source_id == target_id`) — the relationship resolver couldn't match `glma.export` to `export.py`
2. The dependency computation skipped all self-referential edges entirely
3. So cross-file imports like `from glma.db.ladybug_store import LadybugStore` produced no dependency edges

**Fix:** Added `_module_from_import_name()` helper that resolves dotted import names (e.g., `glma.db.ladybug_store`) to module names by matching the last segment against file stems in `file_data`. Updated the dependency loop to handle both resolved and unresolved edges.

**Root cause:** ARCHITECTURE.md was designed to work with resolved cross-file relationships, but glma's Python relationship resolver leaves most imports as unresolved when the target module isn't in the indexed set. This is a fundamental limitation — glma only resolves relationships within the indexed codebase, not to standard library or third-party packages.

---

### 3. Key Interfaces Section Was Empty [FIXED]

**File:** `src/glma/export.py` → `_compute_key_interfaces()`

**Problem:** Key interfaces showed "*(No key interfaces identified)*" because the counting logic only looked at:
1. `direction == "incoming"` relationships (which don't exist for unresolved imports)
2. Resolved cross-file relationships (rare in typical Python codebases)

**Fix:** Changed to count from the source side: for each file's outgoing relationships, if the import is unresolved, match the `target_name`'s last segment against chunk names in other files. This correctly identifies heavily-imported classes like `LadybugStore`, `Language`, `Chunk`, etc.

---

### 4. Entry Point Fan-In Had Too Many False Positives [FIXED]

**File:** `src/glma/export.py` → `_detect_entry_points()`

**Problem:** Almost every file was detected as a "likely entry point" because the fan-in check used `direction == "incoming"` which doesn't exist for unresolved imports — so every file appeared to have zero incoming imports.

**Fix:** Pre-compute `imported_files` set by resolving outgoing imports to target files (using both resolved target_ids and unresolved import names). Then check if each file appears in the imported set. Files NOT in the set + having outgoing relationships = likely entry point.

**Result:** Now correctly identifies `__main__.py` and `cli.py` as entry points, not every file in the codebase.

---

### 5. `--summary-only` Didn't Work for Notebooks [FIXED]

**File:** `src/glma/query/notebook.py`, `src/glma/cli.py`

**Problem:** `glma query notebook.ipynb --summary-only` still included full source code. The notebook dispatch in `cli.py` called `compact_notebook()` without passing the `summary_only` flag, and `compact_notebook()` had no parameter for it.

**Fix:** Added `include_code` parameter to `compact_notebook()` and `_format_cell()`. When `include_code=False`, code cells show `*N lines* — \`first line...\`` instead of the full source. Wired `--summary-only` → `include_code=not summary_only` in the CLI dispatch.

---

### 6. Duplicate Chunk IDs Crash on C Files [NOT FIXED — v2]

**File:** `src/glma/index/chunks.py` → `_chunk_id()`

**Problem:** Indexing Linux kernel C files crashes with:
```
RuntimeError: Found duplicated primary key value 
api.c::class::crypto_alg::38, which violates the uniqueness constraint
```

Multiple structs with the same name at different locations in the same file produce identical chunk IDs. The ID format is `{file}::{type}::{name}::{start_line}` but `start_line` can collide when tree-sitter reports the same start line for nested/macro-expanded declarations.

**Workaround:** Only index Python files for now. C support needs ID de-duplication.

**Proposed fix for v2:** Add content_hash or byte offset to chunk ID to make it unique even when name + line collides.

---

### 7. RELATIONSHIPS.md Nearly Empty for Python Codebases [NOTED]

**File:** `src/glma/export.py` → `generate_relationships_md()`

**Observation:** RELATIONSHIPS.md for the glma codebase was only 137 bytes — essentially empty. The function only shows cross-file relationships, but Python imports within the same package (e.g., `from glma.models import Chunk`) are often unresolved, so they don't appear as cross-file edges.

This is related to issue #2 — the relationship resolver doesn't fully resolve Python imports to file paths. ARCHITECTURE.md now works around this, but RELATIONSHIPS.md still has the limitation.

**Status:** Known limitation, not a regression. Would require improving the relationship resolver to match dotted import names to file paths within the indexed set.

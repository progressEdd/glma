## Problem

The `Chunk` model has a `summary` field, but it's never populated for notebook cells. The summarization pipeline (`summarize_chunks()` in `summarize/pipeline.py`) operates on `Chunk` objects from `LadybugStore` — but notebooks bypass LadybugStore entirely (cli.py: notebook dispatch returns early before touching the DB). So:

1. **Regular source files** — AI summarization works via `glma index --summarize` → `summarize_chunks()` pipeline (Phase 6-7)
2. **Notebook cells** — Never stored as `Chunk` objects, never reach the summarizer. `compact_notebook()` only produces rule-based variable annotations, no LLM summaries.

For a code index meant to help agents quickly understand codebases (including notebooks), per-chunk/cell summaries would be high value — a 1-sentence description of what each cell does, generated by a local LLM.

## Solution

### Already done (Phase 6-7)
- ✅ `SummarizerProvider` protocol with `summarize(code, context) -> str`
- ✅ `LadybugStore.update_chunk_summary(chunk_id, summary)`
- ✅ `summarize_chunks(store, chunks, provider)` pipeline
- ✅ CLI `--summarize`, `--summarize-provider`, `--summarize-model` flags
- ✅ OpenAI-compatible and pi providers

### Still needed: Notebook cell summarization
Two approaches (pick one):

**Option A: Convert cells to chunks, reuse pipeline**
- Parse notebook cells into `Chunk` objects (with `file_path` = notebook path, `chunk_type` = MODULE or a new CELL type)
- Store in LadybugStore alongside regular file chunks
- Run through existing `summarize_chunks()` pipeline
- `compact_notebook()` reads summaries from DB when available
- Pro: Reuses all existing infrastructure
- Con: Notebooks don't chunk the same way as source files; schema may need adapting

**Option B: Direct per-cell summarization in `compact_notebook()`**
- Accept an optional `provider` parameter in `compact_notebook()`
- For each code cell, call `provider.summarize(cell.source, context)` inline
- No DB storage — summaries are ephemeral per invocation
- Pro: Simple, no schema changes
- Con: No persistence, re-runs LLM every time, can't use `--summarize` during index

**Recommended:** Option A — it's more work but aligns with the existing architecture and gives persistent summaries.
